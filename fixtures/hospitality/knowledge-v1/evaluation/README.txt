Hospitality knowledge evaluation fixtures

Purpose
-------

This directory contains an independently authored test oracle for synthetic
guest conversations over the knowledge-v1 corpus. It is a dataset, not an
evaluation runner. Expected outcomes describe compliant behavior; they do not
claim that an app, model, image system, or audio system has been run or passed.

Files
=====

cases.jsonl
    189 independently authored cases, one JSON object per line. Each object
    has a stable case_id, hotel_id, languages, category, turns,
    expected_outcome, required_fact_ids, source_evidence_refs, expected_facts,
    catalog_expectations, expected_constraints, state_delta, tool_expectations,
    clarification_expectations, unknowns, forbidden_claims, media_expectations,
    lifecycle_scenario_ids, timeline_expectations, and status. No-op state
    deltas are empty arrays. Non-empty deltas are operation objects. Timeline
    expectations include route travel and buffer times, venue duration/window,
    rest block, and return time.

coverage.json
    Authored fixture coverage by hotel, referenced facts/sources/catalog items,
    languages, scenario categories, media, and lifecycle. It explicitly says
    execution was not run.

validate_evaluation.py
    Standard-library structure and grounding checks. Run from this directory
    with `python3 validate_evaluation.py`. It validates references, hotel
    isolation, exact fact/catalog values, media paths and scene timecodes,
    lifecycle IDs, and itinerary arithmetic. It does not execute a
    guest-facing system.

Oracle authoring rules
======================

* Scenarios are authored independently. Expected turns are not generated by
  the implementation or a function that the eventual system under test uses.
* Every factual expected value cites a fact ID and matches that fact's typed
  value. Catalog values cite a catalog record and are compared directly with
  properties.json. When sources do not establish a value, mark it unknown and
  ask for clarification where the guest's decision depends on it.
* Keep the three hotel namespaces isolated. Cross-property questions expect
  no cross-hotel fact leakage.
* Coverage includes multi-turn journeys, multi-intent requests, family and
  occupancy questions using authored ages and capacities, reference room
  prices and unknown fees, route timing/buffers/rest/edit/copy, lifecycle
  update/revoke/delete, retention and privacy, prompt-injection resistance,
  session/property isolation, and unavailable source/model/tool conditions.
* Prompts include English and Vietnamese plus a small number of French,
  Japanese, Arabic, Hindi, and mixed-language examples. Language labels are
  test metadata, not a supported-language whitelist or translation certification.
* Media cases cite actual manifest media IDs and visible labels or exact video
  scene boundaries. Media cannot establish guest count, accessibility,
  child safety, guardian rules, or other absent facts. The synthetic-tour MP4s
  are silent; authored captions are not ASR evidence.
* Lifecycle records are isolated test fixtures and never alter the approved
  guest-facing corpus. Each lifecycle case specifies the expected isolated
  action. External destinations are inert `.example` or `.invalid` URLs.

Coverage interpretation
=======================

There are 189 unique cases, evenly split across the three properties. The
cases represent authored source and scenario coverage; see coverage.json for
fact and catalog reference counts. Unreferenced facts remain visible there.
Execution coverage is `not_run`: structural validity does not show that a
system has been tested or passed. The language set does not certify translation
quality. Text fixtures cannot prove real-world computer vision or speech
recognition ability.
